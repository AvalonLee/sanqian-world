# D15 监听体外置 · 可行性勘察（2026-10-19）

> **本件是勘察档，不立判据、不作账本。** 判据最终形态落工程规范，销号唯一落点仍是任务清单「现行未实施表」。
> 全件行数均为 **2026-10-19 现跑实测**，复现口径见 §九；在册读数与实测有差者已逐条标出，未改任何在册文字。

## 一、结论（TL;DR）

1. **D15 可做，但天花板比预期低。** 监听体内可搬体量实测 **347 行** = 派发器 C 类 26 支 **307 行** + 非派发器的天道旨意两处（`mdc-accept` 18 / `mdc-defy` 17）与奏疏解析 5 = **40 行**；扣掉必然留下的转发骨架（26 支 × 1 行 + 3 处监听转发），**净减 ≈ 320 行**，落成后 `view/index.html` **3,130 → ≈ 2,810 行（−10.2%）**。这不是又一次 −450 的刀，是收尾刀。
2. **「只剩一条路」这个前提不成立。** 内核里还有 **6 个呈现族 ≈ 358 行**是前十九刀没切的余量，它们**不需要 D15**：渡劫演出 86 / 财柱浮层 80 / 洗髓 60 / 设置 55 / 离线呈报 43 / 器灵面板 34。复用十九刀已验证的「整族搬 + 桥」形状，风险显著更低。
   ⚠️ **但有一条限制必须写死**（第册五十七批桥位审计的既有结论）：这些族的入口有 2–7 处**核内调用点**（`offlineDetail` 5 / `identityParts` 6 / `showWash` 2 / `renderPillars` 1 …），搬走后核内这些点要改写成 `SQ.UI.<ns>.<fn>(ctx(), …)` —— **桥键能删，但换来的是核→件的反向调用点**。所以「整族搬」要按「核内调用点数」排先后，不是按行数：`renderSpiritPanel`(0) / `showTrib·renderPillars·renderLedger`(1) / `showOfflineReport·showWash`(2) 先做，`identityParts`(6) / `offlineDetail`(5) 这类高耦合族排后或不做。
3. **顺手核出三处账实不符**（详见 §二）：① 在册 `3,119` 实测 **3,130**（+11 行）；② `data-act` 面 **124 产出 ⇔ 130 注册**，产出侧零孤儿，注册侧 `claim` 全仓找不到产出点（疑似死枝）；③ 分派器 **131 个 act 名零重复** ⇒ if 链实为 switch 的伪装，**顺序不承载语义**——这一条显著降低 D15 的风险评级。
4. **建议排期：先低风险整族搬（3 刀，净 −350），再上 D15（1 批判据 + 5 刀，净 −320）。** 若只选一条，选整族搬：减行量相当，风险约为 D15 的三分之一。两条都做完，index.html 落到 **≈ 2,460 行**（自 7,611 起算 −68%）。

## 四、D15 判据设计（草案）

### 4.1 三条判 + 一条豁免机制

| 编号 | 判什么 | 判法 | 今天首跑预判 |
|---|---|---|---|
| **D15①** | **监听体收敛**：`view/index.html` 每处 `addEventListener` 的回调体有效语句数 ≤ 1，且唯一语句 ∈ {`SQ.UI.<ns>.<fn>(ctx(), …)`（可 await）· 一次内核函数调用 · 空转发 `return`} | 词法掩码 + 花括号配对（复用 D13 现成实现）；分派器另算：129 支中 C 类 36 支进豁免表逐支销号 | 51 处里 **16 处不合规**（含派发器）⇒ 全部进初始豁免 |
| **D15②** | **`act` 面双向对表**：渲染面产出 ⇔ 分派器注册面，双向相等 | 产出面三种形状：`data-act="x"` 字面量 ‖ 表字段 `{act:'x'}` 经 `data-act="' + c.act + '"` 渲染（本仓 1 处，`index.html:1171`）‖ 函数实参 `washCard(el, i, 'washSlot')`；注册面 `act === 'x'`（含 `\|\|` 并列） | **124 ⇔ 130**；产出侧**零孤儿**；注册侧 6 枚待裁定——5 枚已解释（3 表字段 + 2 实参），**`claim` 无解释** |
| **D15③** | **跨件调用形状对表**：`SQ.UI.<ns>.<key>(args)` 的实参数 === 导出函数的形参数（`ctx()` 计 1、`el` 计 1、`null` 计 1） | 导出面从 `view/*.js` 现取（D14 已有同源实现），调用面全仓扫 | **今天应零命中**（19 刀都跑过走查）；它补的正是 **D13 自陈的边界**（跨件不在 D13 射程） |

**豁免机制（关键）**：D15 不能在「现状还红」时单独立关——本仓铁律是收口必跑 `npm test`，一条恒红的判据等于门禁失效。因此 D15① 必须**同批**落一张在册豁免表（初始值 = 今天剩下的 16 处监听 + 36 支 C 类分支，逐条带机器归属），此后**只减不增、失效同判红**——这正是审计 **D3** 已在用的形状（在册例外按出现次数钉死）。

**D15③ 建议独立成关**（编号可给 D16）：它的射程不限监听体，且与 D15 的搬迁节奏无耦合；合在 D15 里会让「监听体是否收敛」这条主判被无关失败拖红。

### 4.2 边界（如实）

- 不判「搬走的东西行为是否等价」——那是走查的事，静态判据永远不承担这一维（第十一刀的前科）。
- 不判事件类型语义（`click` / `input` / `focusout` 是否用对）。
- 不判桥值快照失效（`SQ.mutate` 深拷贝世界那条由 `fresh` 纪律管，D15 不管）。
