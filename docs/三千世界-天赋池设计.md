## 一、设计原则

1. **效果全部挂通用系统乘区**：天赋不写死数值逻辑，只声明 `effects` 字段，由对应系统（挂机/战斗/商店/事件/突破）在计算时读取，保证换世界后引擎不用改。
2. **正负分明**：每条天赋要么是纯增益（`positive`）、要么是纯减益（`negative`），不做混合双刃剑——「高风险高回报」的体验由 **组合规则**（1正+2负）提供，而不是单条天赋内部对冲，UI 上玩家一眼能读懂。
3. **池分两层**：`common`（跨世界通用，进任何世界都可抽到）+ 世界专属（如 `xiuxian`，只在对应世界创角时进池）。
4. **稀有度用权重表达**：不设显式 tier 弹窗，强力词条权重低、出现即惊喜；数据结构保留 `tier` 字段仅供配色/展示（普通=常规色，稀有=高亮色）。
5. **重抽规则**（已拍板）：创角阶段无限免费重抽，同一次 roll 内不出现重复词条；点「确认」写入 `profile.talents` 后永久锁定。
6. **机制词条复用既有挂点**（✅ 系统深化批 · 已实施）：除平坦乘区字段外，`effects` 允许以**挂点白名单内的 hook 键**声明条件式/事件式效果（如「瓶颈状态时战力 +5%」），由 `mods.collect` 分流进 `mods.hooks`，与功法特殊属性/法宝签名同通道消费。机制天赋**不得发明新挂点**——只能复用 §三·补 列出的既有消费点；通用池机制词条只用引擎层（systems/）消费的挂点，保证跨世界有效（渡劫类挂点在无渡劫系统的世界自然惰性，见 §三·补 注记）。
7. **稀有度三档**（✅ 系统深化批 · 已实施）：`tier` 枚举扩为 `common | rare | epic`；epic 为修仙专属池独有档（权重 2~3，强度 ≈1.5×rare 或附带机制 hook），古武池暂不启用，详见专属池卷 v1.1。

## 二、数据结构

```js
// talents/common.js / talents/xiuxian.js 中的单条天赋
{
  id: 'gifted',              // 全局唯一，snake_case
  name: '天资聪慧',           // 显示名（未来走 t() 词表）
  kind: 'positive',          // 'positive' | 'negative'
  tier: 'common',            // 'common' | 'rare' | 'epic'（epic ✅ 系统深化批 2026-10-02，修仙专属池独有；仅影响展示配色）
  world: 'common',           // 'common' | 'xiuxian' | …
  weight: 10,                // 抽取权重
  desc: '修为产出 +15%',      // UI 描述（由 effects 生成或手写）
  effects: { qiRate: 0.15 }  // 乘区声明，见 §三；✅ 机制词条可写挂点键（已实施），如 { on_bottleneck_power: 0.05 }，见 §三·补
}
```

### 抽取算法（伪代码）

```js
function rollTalents(worldId) {
  // 1. 决定组合：40% → 1正1负；35% → 2正1负；25% → 1正2负
  const combo = pickCombo();          // {pos: 1|2, neg: 1|2}，pos+neg ≤ 3
  // 2. 组池：common 池 + 当前世界专属池
  const posPool = [...COMMON_POS, ...WORLD_POS[worldId]];
  const negPool = [...COMMON_NEG, ...WORLD_NEG[worldId]];
  // 3. 按 weight 加权无放回抽取
  let talents = pick(posPool, combo.pos).concat(pick(negPool, combo.neg));
  // 4. 单正单负组合 → 正面天赋效果 ×1.5（「极致单一」规则）
  if (combo.pos === 1 && combo.neg === 1) amplify(talents, 1.5);
  return talents;
}
```

> `amplify` 只放大 `effects` 中**对玩家有利方向**的数值 ×1.5（如 `qiRate: 0.15 → 0.225`，`shopCost: -0.10 → -0.15`），显示描述同步重算，保留 1 位小数百分比。
>
> ✅ 系统深化批 2026-10-02 · 已实施（实施收口 2026-10-03）：amplify 对 epic 档正面词条**同样适用**（极致单一 ×1.5）。机制词条的放大分两类——**加算型 hook**（on_bottleneck_power / on_trib_next / mingwang / shikui / on_kill_drop）直接 ×1.5（有利方向，如 `on_bottleneck_power: 0.05 → 0.075`、`mingwang: -0.03 → -0.045`）；**乘算型 hook（yufeng 唯一）**按 `v' = 1 + (v − 1) × 1.5` 换算（`0.90 → 0.85`，仍是玩家有利方向），不能直接 ×1.5（会得到 1.35 的惩罚反向值）。`talents/engine.js` 的 `copyTalent` 无需改动（effects 已是平坦字典，逐键拷贝天然兼容 hook 键）；`amplify` 需加上上述乘算型分支（本批唯一涉及 engine.js 的改动点，其余见 §三·补 实施注记）。

### 三·补、机制挂点键字典（✅ 系统深化批 2026-10-02 · 已实施（实施收口 2026-10-03））

机制型天赋的 `effects` 以下列**既有挂点键**声明（键名与数值口径逐一对照现行消费点核实，禁止发明新挂点）：

| 挂点键 | 语义（与代码消费点一致） | 消费点 | 数值口径 | 对玩家有利方向 |
|---|---|---|---|---|
| `on_bottleneck_power` | 瓶颈状态时战力加算 | `systems/combat.js` `bottleneckOf`（`power = raw × (1 + shikui + bnBond + trBn)`，与尸傀护主/护镖/法宝同读点加算） | 0.05 = 瓶颈战力 +5% | 正 |
| `shikui` | 瓶颈状态时战力加算（尸傀护主同通道） | 同上读点 | 0.08 = +8%；功法侧档位 0.05/0.10/0.15 | 正 |
| `yufeng` | 瓶颈击杀间隔惩罚**乘数** | `systems/combat.js`（`pen *= hooks.yufeng`；pen 基准 3，精≥中等 dc → 2） | 0.92 = 惩罚 ×0.92（瓶颈更快过去）；功法侧 0.8 | < 1 |
| `on_kill_drop` | 每次击杀后的追加掉落掷概率（枯木逢春同通道） | `systems/combat.js` `simulate`（`rolls = 1 + (rand < 追加掷 ? 1 : 0)`） | 0.06 = 6% 概率追加一次独立掉落掷 | 正 |
| `on_trib_next` | 渡劫失败后，下次渡劫判定的一次性成功率补偿 | `systems/realm.js`（与功法 `yiqian` 同通道加算后写入 `ws.tribulation.next`，下次判定消费后清零） | 0.02 = 下次成功率 +2pp（一次性） | 正 |
| `mingwang` | 渡劫失败修为损失减免（不动明王同通道） | `worlds/xiuxian/tribulation.js` `loss`（`loss = 0.5 + ΣtribFailLossMod + 神修正 + mingwang`，clamp 0.30~0.70） | -0.03 = 损失系数 −3pp；功法侧档位 -0.02/-0.05/-0.08 | 负 |

**使用边界**：

- **通用池机制词条**只用引擎层（`systems/`）消费的挂点：`on_bottleneck_power` / `shikui` / `yufeng` / `on_kill_drop` 在一切世界生效；`on_trib_next` 消费点在引擎 `realm.js` 的渡劫失败分支内，**无渡劫系统的世界（如古武）自然惰性**（惰性词条，不报错、不生效），P5 复查是否按世界组池时剔除；`mingwang` 消费点在修仙世界文件内，**只允许修仙专属池使用**。
- 同一挂点键的天赋值与功法/法宝值**同通道合并**，总量仍受各消费点既有 clamp 约束（渡劫 p clamp 0.05~0.95、损失 clamp 0.30~0.70），叠爆由引擎护栏兜底。

**实施注记（引擎改动点，✅ 已实施 2026-10-03：mods.collect 第 1 步分流 + TALENT_HOOK_KEYS 导出，见 systems/mods.js）**：

1. `systems/mods.js` `collect` 第 1 步收集天赋 effects 时，将**命中挂点白名单的键分流进 `mods.hooks`**（与功法/法宝同通道），其余键照旧走 `note(k, 'talent', v)` 入乘区。白名单 = 世界包 `pack.specialHooks` 的 pool 键 ∪ 引擎消费的裸 hook 名（上表 6 键）。`talents/engine.js` `copyTalent` **无需改**（effects 已是平坦字典）；`amplify` 的乘算型换算见 §二注记。
2. **乘算型合并规则（yufeng）**：分流时不能与功法档位简单加算（0.8 + 0.92 = 1.72 会把乘数叠反）。collect 对 `yufeng` 键按**乘算合并**：`hooks.yufeng = Π(各来源值)`（功法 0.8 × 天赋 0.92 = 0.736）。⚠ 顺带登记现行缺陷：功法侧多部御风系（云纵/流影/云游/太虚）目前在 collect 第 2 步**加算**叠加（两部 0.8 → 1.6，惩罚反增），本批分流改造时统一改为乘算合并，`combat.js` 读点 `pen *= hooks.yufeng` 不变。
3. **on_kill_drop 双键加算**：现行 `combat.js` 追加掉落掷只读 `hooks.fengchun`（功法池键）+ `bonds.dropExtra`（道友通道）；天赋侧用裸 hook 名 `on_kill_drop`（挂点白名单内 `fengchun` 池映射的 hook 名），实施时把该读点扩为 `fengchun + on_kill_drop + dropExtra`（一行，与 `realm.js` 的 `yiqian + on_trib_next` 双键加算同款模式）。`on_trib_next` / `on_bottleneck_power` / `mingwang` / `shikui` / `yufeng` 五键消费点**零改动**（realm.js / combat.js / tribulation.js 已按这些键名读取）。
4. **词表**：机制词条 name/desc 进 `lexicon` `talent.{id}.name/.desc`（词表 key 纪律同现行词条）；`effectsToText` 自动生成需要 `talent.field.{挂点键}` 标签（如 `talent.field.on_bottleneck_power = '瓶颈状态时战力'`），标签文本自带条件句式，乘算型（yufeng）标签建议 `talent.field.yufeng = '瓶颈间隔'` 且描述手写不走自动生成（乘数不是百分比口径）。
5. **羁绊来源**（§九）：`collect` 新增第 11 步遍历 `pack.data.TALENT_SYNERGIES`，`note(field, 'synergy', value)`；`detail` 初始化行补 `synergy: 0` 键。

## 六、组合期望与平衡说明

### 6.1 单次 roll 的组合分布

| 组合 | 概率 | 正面强化 | 体验定位 |
|---|---|---|---|
| 1 正 + 1 负 | 40% | 正面 ×1.5 | 极致单一：一个鲜明长板 + 一个短板 |
| 2 正 + 1 负 | 35% | 无 | 主流均衡 |
| 1 正 + 2 负 | 25% | 无 | 高风险高回报（未来可考虑给额外补偿，见 §6.3） |

### 6.2 专属词条出现率（修仙世界创角，v1.3 二轮扩容后；历史口径——系统深化批扩容后已由 §6.4 取代）

- 正面池：28 通用 + 40 专属 = 68 条；专属词条权重占比 ≈ **53%**——平均每次 roll 的正面位一半以上是修仙专属；稀有专属（雷灵根/历劫之躯/剑道奇才/天道垂青等 14 条）合计权重占比 ≈ **16%**，平均 6 次重抽见一次，惊喜感保留；
- 负面池：22 通用 + 40 专属 = 62 条；专属负面权重占比 ≈ **61%**——短板的世界观味道进一步拉满；
- 扩容守则复盘（两轮均执行）：全部词条只用 §三 字典字段、单条幅度不超过同乘区既有最大值（tribFailLossMod 最深仍为历劫之躯 -0.15，新增 -0.06/-0.08 均在其下）、稀有度用权重表达（稀有 4~5 / 普通 6~8）；
- **词条密度控制**：同一乘区的近似词条（如 qiRate 系）刻意保留梯度（+3%~+15%），组合期望见 §6.3。

### 6.3 平衡待办（P5 复查）

1. **1正+2负 是否给补偿**：当前无额外补偿，纯靠玩家自愿选择。若数据上没人选，可加「逆境之子」隐藏修正（如全乘区 +5%）；✅ 系统深化批已落地替代钩子——§九 羁绊 `syn_trib_lightning`（正负混对「劫雷一线」），1正1负 / 1正2负 组合均可触发，P5 先观察该羁绊选取率再决定是否加全局补偿；
2. **`tribBonus` 上限核对**：雷灵根(+0.15) + 道心通明(+0.08) 若同时出现（2正组合），叠加装备/善恶后 p 已被 `clamp(…, 0.95)` 封顶，无需额外处理，但要在冒烟测试里验证 clamp 生效；✅ epic 档已加入、clamp 兜底由 #167/#171 覆盖（真仙裸身最坏 0.308 断言）：混沌雷灵根(+0.22)、凤凰浴雷羁绊(+0.05)、极致单一 amplify(×1.5) 三者叠满时仍由同一 clamp 兜底，冒烟测试用例补一行；
3. **`combatPower` 与渡劫的联动**：`combatPower` 修正会间接抬高 resistBonus 战力项（`(战力/境界基础战力−1)×0.15`，封顶 0.15），剑骨(+15%)的实际渡劫收益已被该项封顶自然约束，P5 按数值详设 §6.3 对表复核即可；
4. **amplify ×1.5 的舍入**：统一「乘后四舍五入到整数百分比」，避免 0.225 这类三位小数进 UI；
5. **tribFailLossMod 深浅核对（✅ 深化批已实施，clamp 断言待 P5 复查补 UI 浮层核对）**：历劫之躯(-0.15) 与 epic 凤凰涅槃(-0.12 + mingwang -0.05) 同 roll（2正组合）合计 -0.32，理论损失 0.5−0.32+神修正 会被 `clamp(0.30, 0.70)` 截在 0.30——P5 验证 clamp 生效且 UI 损失预估浮层显示截断后值；epic 负面「道基崩碎」(+0.15) 叠加神修正最深 0.75 → 同样被 clamp 0.70 兜底；
6. **机制词条惰性口径（✅ 引擎侧惰性已实施——古武 roll 到不报错不生效；UI 灰显口径待 P5 决定）**：古武创角 roll 到 `on_trib_next` 词条时不报错、不生效（§三·补），但 UI 描述会让玩家困惑——P5 决定「按世界组池时剔除渡劫类挂点词条」还是「描述显示灰色（本世界不生效）」，倾向后者（保留跨世界词条一致性，改动只在 view 层）。

### 6.4 扩容后出现率估算（✅ 系统深化批 2026-10-02 · 已实施（实施收口 2026-10-03））

> 算法与 §6.2 一致（加权抽取，逐位独立估算）；权重合计按 §四（含 4.1.1/4.2.1/4.3）与专属池卷 v1.1（5.3/5.4/5.5）全表加总。修仙世界创角口径：

- **池规模**：正面池 = 通用 40（平坦 36 + 机制 4）+ 专属 66（平坦 52 + 机制 6 + epic 8）= **106 条**，权重合计 277 + 346 = **623**；负面池 = 通用 32 + 专属 58 = **90 条**，权重合计 227 + 348 = **575**；
- **专属词条权重占比**：正面 ≈ **55.5%**（v1.3 为 53%）、负面 ≈ **60.5%**（v1.3 为 61%）——两轮平坦扩容刻意在通用侧多补 checkBonus/attrBonusAmp 等新字段，专属占比基本持平，世界观味道不被稀释；
- **稀有档合计（正面板）**：旧稀有 14 条（权重 68，占 10.9%）+ 新稀有平坦 4 条（通用老练直觉/大器晚成 10 + 专属道眼如炬/道果迟熟 10）+ 机制 10 条（通用 18 + 专属 25）+ epic 8 条（20）= 权重 151，**占全正面池 ≈ 24.2%**——高稀有感词条密度显著上升，但其中最大头是机制档（43，≈6.9%），平坦旧稀有的单位惊喜度未变；
- **epic 期望**：epic 正 8 条权重 20（单条 w2 词条单位出现率 ≈0.32%，w3 ≈0.48%）+ epic 负 2 条权重 5；**每个正面位出 epic 概率 ≈3.2%**，按组合分布（平均正面位 1.35 / 负面位 1.35）折算**每次 roll 至少 1 条 epic 的概率 ≈5.4%，约 18 次重抽见一次**——与「稀有 6 次一见」（§6.2）拉开两档梯度，顶级词条维持惊喜感；

- **词条密度控制**（沿用 §6.2 守则）：新增全部只用 §三 字典字段与 §三·补 挂点键；单条幅度不超同乘区既有最大值（tribFailLossMod 最深仍为 epic 道基崩碎 +0.15 < clamp 兜底；正向最深凤凰涅槃 -0.12+mingwang -0.05，均未越过历劫之躯 -0.15 的单键极值太多且有 clamp 护栏）；epic 档权重 2~3 / 机制档 4~5 / 平坦档 5~8，三档梯度清晰。

2. 每条声明 `world: '{worldId}'`，效果只用 §三 字典中的通用字段（新世界专属字段需先在设计文档登记）；✅ 机制词条（§三·补）同样可用（已实施），但只限引擎层消费的挂点键；世界文件内消费的挂点（如修仙 `mingwang`）只能进对应世界专属池；
3. 专属池规模标准（v1.3 修订）：新世界**首发 ≥24 条**（正负各 12，最小完整集）；进入内容成熟期后**对齐修仙/古武标准 80 条**（正负各 40）；至少 2 条与该世界的 **专属系统** 互动（对标修仙的渡劫词条、古武的 gateMod/bannerBoost 词条）；✅ 系统深化批注（已实施，实施收口 2026-10-03）：修仙 124 条是深化批的**先行试点扩容**（机制/epic 维度），80 条仍是新世界成熟期基准线，机制/epic 维度是否跟进由各自世界批次评估后再修订本标准；
4. 在 `registry.js` 世界包中挂 `talentPool` 引用，创角屏 2 自动按 `worldId` 组池；✅ 世界包 `data.js` 可挂 `TALENT_SYNERGIES`（§九，修仙包已挂 8 对），未声明即无羁绊，既有行为零变化。

## 九、组合羁绊 TALENT_SYNERGIES（✅ 系统深化批 2026-10-02 · 已实施（实施收口 2026-10-03））

### 9.1 定义

- **生效条件**：锁定后的 `profile.talents` **同时含配对的两条词条**（不分正负、不分通用/专属，跨池可配）；创角重抽阶段不生效，确认锁定后永久生效（与天赋同生命周期）。
- **加成通道**：走 `mods.collect` 新来源 `'synergy'`（实施注记见 §三·补 第 5 条：collect 新增第 11 步遍历 `pack.data.TALENT_SYNERGIES`，pair 全部命中 → `note(field, 'synergy', value)`；`detail` 初始化行补 `synergy: 0` 键，UI 明细浮层自动多一行「羁绊」来源）。
- **幅度纪律**：单对只加成**一个** §三 字典乘区字段，`|value| ≤ 0.05`；羁绊值不 amplify、不吃 tier 权重（它是组合奖励不是词条）。
- **常量位置**：`TALENT_SYNERGIES` 挂世界包 `data.js`（配对成员可来自通用池；纯通用对也先只在修仙包声明，古武世界开放时按需复用）。同一词条可参与多对，但同 roll 最多 3 条天赋，天然最多同时命中 1~3 对（2正组合可命中 1 对正正羁绊，1正2负可命中正负混对）。
