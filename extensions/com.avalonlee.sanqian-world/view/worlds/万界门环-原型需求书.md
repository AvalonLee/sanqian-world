## 一、项目背景（60 秒）

**三千世界**（`sanqian-world`）是一个**多世界游戏合集**，以浏览器扩展（x-hub extension）形态交付：每个「世界」相当于一份独立资料片，各自探索不同的玩法与技术——整个项目是作者的 vibecoding 实验，用于探索 AI 编程与技术的上限。当前两个世界已上线：

| 序 | 世界 | 形态 | 入口（相对本目录） |
|---|---|---|---|
| 第一世界 | **仙侠世界**（玄幻修仙） | 放置修仙人生模拟 | `../index.html` |
| 第二世界 | **侠影世界**（金庸语料武侠） | 3D 山河棋盘冒险 RPG | `../games/qunxia3d/index.html` |
| 第三世界起 | 未公开 | 资料片筹备中 | 无（占位剪影门） |

玩家启动时**先经「万界门环」选世界，再进入该世界的创角流程**。本需求书只管「万界门环」这一页；两个世界本体各有自己的代码与文档，不在本件范围内。

## 二、核心概念（已拍板，不可更改）

**万界门环 = 环形回廊 + N 扇世界之门 + 门内活世界缩影 + 推门入世。** 三条灵魂判据：

1. **门环**：世界之门排成一环，玩家沿环巡视——「环」是空间组织方式，也是「万界并列」的隐喻。
2. **门内有活景**：门面不是一张静态贴图，而是**通往该世界的窗口**——门内呈现该世界意象的**动态缩影**（活的：有动效、有呼吸）。「每扇门后有一个正在运转的世界」是本方案的灵魂。
3. **推门分流**：走近 → 门苏醒 → 推门 → 过渡演出 → 进入该世界的入口页。

视觉与空间氛围如何诠释这三条，**完全由实现方发挥**（见 §六、§九）。

## 三、功能需求（F1~F8，逐条可验收）

| # | 需求 | 验收口径 |
|---|---|---|
| F1 | **世界注册表驱动**：页面内容（门数、门名、分流目标、开放态）全部来自一张独立的世界注册表，**新增一个世界 = 注册表加一张卡**，选择器零改动 | 改注册表（如把第 3 张卡改为 open）后刷新，门环出现新开放门并可分流 |
| F2 | **开放门 / 剪影门两态**：`status:'open'` 的世界是可进入的完整门；`status:'coming'` 是剪影/封印门——**可被注视但不可进入**（点击不产生信息卡+推门钮，或给出「未开放」反馈） | 3 卡注册表下：2 扇可进入，1 扇不可 |
| F3 | **环视交互**：拖拽（鼠标按住横移）旋转视点环视门环，相机平滑追踪（缓动，无跳切）；支持松手后惯性或缓停任一 | 拖拽可见其余门扇依次掠过 |
| F4 | **走近与苏醒**：点击某扇开放门（或等价的选中操作）→ 相机推进到该门正前方 → 该门**苏醒**（专属光效/粒子渐显，一扇苏醒时其余门回落）→ 弹出**信息卡**（印章字、世界名、`序号 · 标语`、描述）与**推门钮** | 对每扇开放门分别成立；剪影门不触发 |
| F5 | **推门分流**：点推门钮 → **约 0.9s 全屏过渡演出**（如白光纱幕渐染）→ `location.href` 跳转该世界的 `path` | 浏览器 URL 变为目标入口页 |
| F6 | **回主壳钮**：页面常驻一个「回主壳」入口，跳 `../index.html` | 点击后 URL 为主壳 |
| F7 | **调试把手契约**（自动化走查依赖）：① `window.__QX3D_READY` 在场景可交互后置真；② `window.__focusGate(index)` 以注册表下标程序化聚焦任一门（含剪影门聚焦但不给推门）；③ 页面根脚本挂 `window.__errs = []` 并以 `window.addEventListener('error', …)` 收集运行期错误 | 走查脚本依赖此三者 |
| F8 | **零控制台错误**：完整交互流程（载入→环视→逐门聚焦→推门）全程无 pageerror / console.error | `window.__errs.length === 0` |

### F1 附：世界注册表 schema（字段固定，数据可增）

`world-registry.js` 挂 `window.WORLD_REGISTRY` 数组，每张卡：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 世界唯一 id（如 `'xiuxian'` / `'wuxia'`） |
| `seq` | string | 序号名（`'第一世界'`…），用于门匾与信息卡 |
| `name` | string | 世界名（门匾主文字） |
| `tagline` | string | 一句标语（信息卡副题） |
| `desc` | string | 两句内简介（信息卡正文） |
| `path` | string\|null | 入口页相对路径；**`null` = coming 态** |
| `status` | `'open' \| 'coming'` | 开放态 |
| `hue` | number | 该世界色相（0~1），供程序化取色 |
| `mist` / `peak` | 0xRRGGBB | 该世界意象色（雾色 / 山色，用途由实现定） |
| `particle` | 0xRRGGBB | 该世界粒子/光效主色 |
| `seal` | string | 一字印章（信息卡与门匾用，如 `'仙'` `'侠'`） |

## 五、上游集成点（本页不实现，但必须共存）

1. **主壳启动重定向**：主壳入口页（`view/index.html`）body 首行有一段双存档检测——`sanqian-state-v1`（修仙存档）无 profile **且** `shanqian3d_save_v1`（侠影存档）不存在 ⇒ `location.replace('worlds/index.html')` 跳入门环。**已有任一世界存档的老玩家不重定向**。门环是「新玩家的第一屏」，首因效应由本页承担。
2. **双端回环入口**：修仙主壳与侠影世界页尾部各有一枚 `🌐 万界` 浮动链接指向本页——玩家随时可回门环换世界。
3. 因此本页必须做到：**从冷启动直达可玩**（file:// 直开无服务）、**来回跳转无状态残留**（不写任何 localStorage 键；`location.href` 直接跳即可）。

## 六、体验质量要求（Q1~Q6，风格中立，验收按此判）

- **Q1 可读性红线**：门匾/门名文字**任何情况下完整置于门框内**（自适应缩放或等价手段）；信息卡文字在最终视觉下清晰可读；**环境不得暗到门体与文字不可辨认**（「黑乎乎一团」= 不合格）。
- **Q2 氛围主体**：页面必须有明确的**非日常空间氛围主体**——它是什么风格完全开放（深空星海 / 水墨长卷 / 仙宫殿堂 / 万流归一的信息场……皆可），但必须让玩家第一屏就感到「这不在寻常世界里」。*用户偏好参考（是信号不是约束）*：用户曾对上一版点名「背景改成宇宙星辰、每颗星缓慢闪烁」「环境太黑」「门上的字溢出门框」——**缓慢闪烁的星体、明暗可读性、文字不入框不可超界**，这三条底线偏好请默认继承，其余视觉决策自主。
- **Q3 门内活景**：每个开放世界的门内是该世界意象的**动态缩影**（内容自定：山河/建筑/人物/符号皆可），必须有持续动效（呼吸/流动/旋转/闪烁任一），不得是静帧。
- **Q4 动效节奏**：相机推进/回落用缓动（0.05~0.1 lerp 或等价）；苏醒渐显；推门过渡约 0.9s；所有转场不得跳切。
- **Q5 性能与体积**：桌面浏览器（Chrome/Edge）60fps 目标；`devicePixelRatio` 上限 2；**零联网依赖**（无 CDN、无外链纹理字体——宿主环境是 file:// 与扩展包）；选择器页新增体积尽量 ≤ 200KB（不含 three.js 时）。
- **Q6 输入兼容**：鼠标必保；触摸单指拖拽视点为加分项（非硬性）。

## 七、技术契约（入库形态；仓外原型阶段见 §九）

1. **零构建**：无打包器、无框架、无 npm 依赖注入——全部是经典 `<script>` 脚本，改完刷新即生效。
2. **three.js 就地取材**：仓库已 vendored `../games/qunxia3d/three.min.js`（~668KB 压缩版，全局 `THREE`），本页**复用它**，不重复携带副本。
3. **自包含子应用**：本目录三件（`index.html` + 渲染层 js + `world-registry.js`）自己就是完整页面；专用样式与脚本放本目录，不进全局资产、不进其他页面。
4. **渲染技术路线开放**：WebGL/three.js 是现行路线；若原型阶段（仓外）想用别的技术（WebGPU、原生 Canvas、播放视频门……），先在仓外验证，入库时须满足 §七.1~§七.3 与 §八验收。
5. 已知技术暗礁（现行实现趟过，换实现时留意）：
   - **Points 近相机负 `gl_PointSize` 方块伪影**（ANGLE/SwiftShader 实测）：粒子中心进入相机近平面会渲染成黑方块——对策：粒子群与相机轨道保持几何隔离 / 顶点着色器加相机背后裁剪哨 / 软圆点精灵贴图。
   - **门内缩影必须有光**：Lambert/Standard 材质无灯即全黑，门内景先打光再看。
   - **门匾文字宽度不可假设**：CJK 字宽随字体回退浮动，必须 `measureText` 自适应。
   - **renderTarget 门中门**：每扇开放门一个离屏 `Scene + Camera` 渲到 `WebGLRenderTarget(512×512)`，门面材质采样该纹理——这条「门即窗口」的现行实现方式可沿用也可替换。

## 九、交付模式与「不约束」清单

**交付模式二选一**：

- **模式 A（推荐给纯原型探索）**：仓外交付**单个自包含 HTML**（或 html+js 少量文件），双击可开、无任何依赖安装。风格与技术栈完全自由。入围后再由仓内 agent 按 §七契约移植入库。
- **模式 B（直做可入库版）**：直接按 §三/§四/§七/§八 产出三件套（`index.html` + 渲染层 js + `world-registry.js`），文件名与 id 契约全对齐，交付即可通过现有走查。

**本件不约束（实现方自主，鼓励大胆探索）**：

1. **美术风格**——题材诠释、配色、建模/渲染风格、UI 材质与字体、粒子与光的语汇，全部开放；
2. **3D 场景内容**——回廊里有什么、门内景画什么、加什么演出，开放；
3. **原型阶段技术选型**——模式 A 下渲染技术、代码组织开放；
4. **交互的表层形态**——§三固定的是「能力」，不是具体控件样式（如 F4 的「点击」可替换为走近自动触发，只要能力等价且可被 `__focusGate` 程序化驱动）。

**交付物**：① 原型本体；② 一段话风格意图自述；③ §八判据的自证记录（截图/录屏或断言脚本输出）。
